# 美妆数据看板 · 架构方案（基于实测数据结构）

> 版本 v1.0 · 2026-09-25
> 依据：罗盘实测手册 + 蝉妈妈实测手册 + 需求与可用数据总览 v2.0
> 约束：你要「全自动定时更新」「业务能跑通」「能路演」；现有工作台是单文件静态页 + 资料库数据表

---

## 〇、先回答「资料库表 + 定时任务」还是「重建采集管道」

**我的判断：走「资料库表 + 定时任务」，不重建采集管道。**

理由（都来自实测，不是拍脑袋）：

| 实测事实 | 对架构的含义 |
|---|---|
| 罗盘接口签名（msToken/a_bogus）每次变，**必须在页面上下文 fetch** | 采集必须走**真实浏览器**（你现有 Chrome + 登录态），无法用纯后端爬虫 |
| 蝉妈妈请求体加密，**不要解密**，从 DOM 读 | 同上，采集 = 浏览器自动化 |
| 商品榜 TOP200、店铺榜 TOP200、类目树 7447 节点、成分榜按品类 | **数据体量很小**——每天全量抓一遍也才几百条，不需要分布式管道 |
| 增速口径 = 两段不重叠 7 天窗口做比值 | 需要**每日快照历史**来算环比，不是只存最新值 |
| 现有工作台数据已存 WorkBuddy 资料库「全球新品库」表 | **存储层已有载体**，不用换 |

**结论**：体量小 + 必须走浏览器 + 已有资料库表 → 架构应该是**「浏览器采集脚本 + 口径统一 + 资料库表（主表+快照）+ 单文件看板」**，而不是重型后端。

## 一、推荐架构：四层分离

```
┌─────────────────────────────────────────────────────┐
│  采集层   浏览器自动化（kimi-webbridge，带登录态）      │
│           罗盘 / 蝉妈妈 / 飞瓜（同事）/ FastMoss        │
├─────────────────────────────────────────────────────┤
│  口径层   统一字段名 · 统一单位 · 统一时间窗            │
│           区间值 → 决策字段（涨/跌/机会分）             │
├─────────────────────────────────────────────────────┤
│  调度层   每日定时（增速）/ 每7天定时（趋势/成分）       │
│           增量更新，失败重试，登录失效则告警            │
├─────────────────────────────────────────────────────┤
│  存储层   WorkBuddy 资料库数据表                       │
│           主表（最新状态） + 快照表（每日历史）          │
├─────────────────────────────────────────────────────┤
│  展示层   单文件 HTML 看板                             │
│           自用密度模式 / 路演结论模式（同一份数据）      │
└─────────────────────────────────────────────────────┘
```

## 二、每层怎么设计

### 2.1 采集层：浏览器自动化脚本

**形态**：Python 脚本，通过 kimi-webbridge 驱动你现有的 Chrome（带罗盘/蝉妈妈登录态）。

**为什么不用纯 requests**：罗盘 `msToken`/`a_bogus` 每次变、蝉妈妈请求体加密——纯后端调不通，必须借浏览器的登录态和页面上下文。

**采集任务清单**（按你的四个模块）：

| 任务 | 数据源 | 频率 | 产出 |
|---|---|---|---|
| 增速产品榜 | 罗盘 `product_rank/market_hot_sale`（面部洗护/眼部护理，各取两段 7 天窗口） | **每日** | 每类目 TOP 商品 + 支付金额区间 |
| 类目增长趋势 | 罗盘 `category_overview_price_band_distribution` | 每 7 天 | 各 `cate_*` 指标 + `out_period_ratio` |
| 机会分 | 罗盘 `dig_cate_list` | 每 7 天 | `pay_amt_incr_rate`/`demand_supply_rate` |
| 市场规模（国内） | 罗盘 `shop_rank` | 每 7 天 | TOP200 店铺/商品 GMV 区间 |
| 成分增长榜 | 蝉妈妈 美妆属性分析 | 每 7 天 | 成分/功效榜（名称/关联商品数/销售额/环比） |
| 竞品产品维度 | 蝉妈妈 商品详情页 | 每日（对 TOP 竞品） | 成分/卖点/备案号/带货结构 |
| 竞品用户维度 | 蝉妈妈 品牌/达人详情页 | 每 7 天 | 受众画像 |
| 竞品视频维度 | 蝉妈妈 黄金3秒台词 | 每 7 天 | 台词/关联视频数/销量 |

**关键设计**：采集脚本只负责「**把页面上的数原样抓下来**」，不做任何计算——计算交给口径层。这样数据源变了只改采集，不动逻辑。

### 2.2 口径层：统一成「决策字段」

这是你「字段太多」痛点的解法。采集来的原始字段（42 个）→ 收敛成每层漏斗需要的**决策字段**：

| 漏斗层 | 原始字段（实测） | 口径层产出（决策字段） |
|---|---|---|
| 找机会 | 罗盘 `new_pay_amt`（区间）+ 两段窗口 | `增速%`、`是否TOP3`、`类目` |
| 看市场 | 罗盘 `pay_amt` TOP200 榜单 | `市场规模`、`CR4`、`CR10` |
| 看竞品 | 蝉妈妈 成分/功效/带货结构/受众画像 | `竞品卡片`（价格带/差评率/卖点/受众） |
| 下决策 | 上面所有 | `机会点`（罗盘 `demand_supply_rate` + 增速 + 竞争度合成） |

**口径层的硬规则**（沿用你的采集手册铁律）：
- 罗盘区间值与蝉妈妈预估值**绝不混加**
- GMV 主口径只信罗盘
- 每个数字带**口径徽章**（来源 + 时间窗 + 区间/精确）

### 2.3 调度层：定时 + 增量

- **每日**：增速产品榜（要日粒度环比）
- **每 7 天**：类目趋势、成分榜、市场规模、竞品画像
- 增量更新：只抓变化的部分，不每次全量
- 失败处理：登录失效 → 停下来通知你手动登录（不硬闯，避免封号）；接口报错 → 记日志重试

调度方式：本地 `launchd`（macOS 定时）跑采集脚本，写回资料库表。

### 2.4 存储层：主表 + 快照表

沿用现有 WorkBuddy 资料库，但**拆成两张表**：

| 表 | 内容 | 用途 |
|---|---|---|
| **主表**（全球新品库，现有） | 每个商品/类目的**最新状态**（42 字段精简后） | 看板当前展示 |
| **快照表**（新增） | 每日/每周的**历史快照**（日期 + 类目 + 指标值） | 算环比增速、画趋势曲线 |

**为什么需要快照表**：增速 = 今天窗口 ÷ 7 天前窗口。如果没有历史，每次都要现算两段窗口；有了快照，直接读历史值。**这也回答了「每日更新」的载体问题**——每日采集往快照表写一行。

### 2.5 展示层：单文件看板，双模式

沿用现有「单文件 HTML + 资料库数据表」的形态（它已经被验证能跑、能发布到 workbuddy.link 路演），但重构信息架构：

- **数据读取**：页面加载时从资料库表读（主表 + 快照表）
- **双模式**：同一个开关切「自用密度模式」（42 字段全展开）/「路演结论模式」（只出结论卡片 + 机会点）
- **板块**：按你定的 7 板块（全球数据看板 / 商品榜 / 成分库 / 初步判断策略 / 竞品分析 / 产品分析 / 产品设计）

## 三、为什么不是「重建采集管道」

| 方案 | 为什么不适合 |
|---|---|
| 纯后端爬虫（requests + 数据库） | ❌ 罗盘签名、蝉妈妈加密，绕不过风控 |
| 重型管道（Kafka/Airflow） | ❌ 数据体量太小（每天几百条），杀鸡用牛刀 |
| 第三方电商数据 API | ❌ 你要的是罗盘/蝉妈妈/飞瓜的特定口径，通用 API 给不了 |
| 现有形态不换 | ⚠️ 现有是「一次性写入、无定时」——**要加的是调度层和快照表，不是推翻重写** |

## 四、落地顺序（配合「先跑通最小闭环」）

```
第 1 步：采集层跑通一个任务（罗盘·面部洗护·增速榜，每日）
        ↓ 验证登录态、字段、写表
第 2 步：加口径层（增速计算）+ 快照表（存历史）
        ↓ 验证增速数值正确
第 3 步：展示层单板块（全球数据看板·增速产品看板）
        ↓ 路演看一眼
第 4 步：复制到眼部护理 → 再扩到其它任务（类目趋势/成分/竞品）
```

**每一步都可独立验证**，符合你说的「先跑通这两个类目，验证顺利再扒其他」。

## 五、待你拍板的 3 个决策点

| # | 决策点 | 选项 | 我的倾向 |
|---|---|---|---|
| D1 | 采集脚本跑在哪 | ① 你的 Mac（launchd 定时，依赖你电脑开机+Chrome 登录）② 一台常开的服务器/工作机 | **① 先用你的 Mac 跑通**，跑稳后再迁常开机器 |
| D2 | 快照表存多久 | ① 只存近 90 天（够算环比）② 长期存 | **① 近 90 天**，够用且表不膨胀 |
| D3 | 竞品数据采集归属 | ① 我顺手把蝉妈妈竞品采集也写进同一套脚本 ② 等同事用飞瓜做 | **① 蝉妈妈部分我先做**（产品/用户/视频维度我已实测），飞瓜筛选留给同事 |
