## 〇、一页看懂：本项目要用罗盘拿什么

| 需求板块 | 用罗盘哪个模块 | 用哪个接口 | 关键字段 |
|---|---|---|---|
| **增速产品看板**（每类目 TOP3，每日） | 市场 → 市场排行 → 商品榜单 | `product_rank/market_hot_sale` | `new_pay_amt`、`rank`、`product_info` |
| **类目增长趋势**（近 30 天，7 天刷） | 市场 → 行业机会 → 类目概览 | `category_overview_price_band_distribution` | `cate_pay_amt`、`out_period_ratio` |
| **成分增长榜联动**（点类目跳成分） | 类目概览 / 类目挖掘 | 类目树 `cate_list` | `category_id`（级联 cid） |
| **市场规模看板**（国内） | 市场 → 市场排行 → 店铺/商品榜单 | `shop_rank` / `market_hot_sale` | `pay_amt`、`pay_cnt` |
| **竞品增速参考** | 市场 → 竞争分析 → 竞争概览 | （竞对追踪） | 交易增速、流量增速 |
| **机会识别**（参考口径） | 市场 → 行业机会 → 类目挖掘 | `dig_cate_list` / `dig_cate_cards` | `pay_amt_incr_rate`、`demand_supply_rate` |

**铁律**：罗盘所有金额/数量都是**区间值**（如 ¥1,000万-¥2,500万），不是精确值。要精确值需换数据源（手册规定 GMV 主口径信罗盘，但其精度只到区间）。

## 一、接口调用基础

### 1.1 认证与公共参数

所有业务接口走 `https://compass.jinritemai.com/compass_api/`，**必须带 cookie 会话**（在用户 Chrome 里已登录）。

| 参数 / 头 | 作用 | 备注 |
|---|---|---|
| `Cookie` | 登录态（sessionid 等） | 过期会让用户在浏览器手动登录一次 |
| `x-e2e-platform: compass` | 平台标识 | 必带 |
| `agw-js-conv: str` | 响应编码 | 建议带 |
| `verifyFp` / `fp` | 设备指纹 | 页面自动生成 |
| `msToken` / `a_bogus` | 签名 | **每次请求会变化**，从页面上下文里取，不能硬编码 |
| `_lid` | 请求 id | 页面自动生成 |

**最稳妥的取数方式**：**在页面上下文里 `fetch`**（`credentials:"include"`），而不是在外部拼 URL 硬调——签名参数由页面生成，外部拼会被风控。

### 1.2 响应的通用结构

罗盘把数据装进两种容器：

**① 直接数组**（如商品榜）：`data.data_result[]`

**② 通用表格容器**（如店铺榜、类目挖掘）：`data.module_data.<模块名>.compass_general_table_value`——这是一个 **JSON 字符串，需要二次 `JSON.parse`**，解出后是：

```
{
  basic_meta: [ {index_display: "中文列名", index_name: "英文字段名", index_tip: "官方口径说明", children: …} ],
  data: [ { cell_info: { <字段名>: { cell_type, index_values / value / … } }, extra: {…} } ],
  page_result: { page_no, page_size, total },
  data_key_list, meta, extra
}
```

**`basic_meta` 是宝藏**：它自带每个字段的中文名、英文名、官方口径说明——写文档时以它为准，不要自己猜。

### 1.3 数值的 `unit` 枚举（实测反推）

| unit | 含义 | 例子 |
|---|---|---|
| 1 | 文本 | `value_str: "90以上"` |
| 3 | 金额（分） | `value: 300000000000` = ¥30 亿 |
| 4 | 百分比小数 | `value: 0.55` = 55% |
| 5 | 数量 | `value: 10000000` = 1000 万 |
| price | 金额（区间端点） | `value_range: [{unit:"price", value}]` |
| number | 数量（区间端点） | 同上 |
| ratio | 比率小数（区间端点） | 同上 |

## 二、时间系统（本项目最关心的部分）

### 2.1 `date_type` 枚举 → 可选日期范围

来自 `GET /compass_api/config_center/data_range_v2?data_type=shop_market_category_overview` 实测（2026-09-25）：

| date_type | 推断含义 | 最早可选 | 最晚可选 | 跨度 |
|---|---|---|---|---|
| 2 | 近1天 | 2026-06-25 | 2026-09-23 | 90 天 |
| **7** | **自然日（自定义，最长）** | **2025-12-31** | **2026-09-23** | **266 天** |
| 8 | 近1天（最短变体） | 2026-09-20 | 2026-09-23 | 3 天 |
| 20 | 近1天（常用） | — | — | — |
| **21** | **近7天（页面默认）** | **2026-09-17** | **2026-09-23** | **6 天** |
| 22 | 近7天（短变体） | 2026-09-21 | 2026-09-23 | 2 天 |
| **23** | **近30天** | **2026-08-25** | **2026-09-23** | **29 天** |
| 24 | 自然月 | 2026-06-26 | 2026-09-23 | 89 天 |
| 29 | 自然周 | 2026-09-10 | 2026-09-23 | 13 天 |

- `common_use_type` = `[20, 21, 23, 2, 3, 4]`（页面上默认展示的选项）
- 数据**截止到前一天**（2026-09-25 当天，最晚只能选到 09-23/09-24）
- 大促窗口在 `activity_info` 里单独列（如中秋团圆季 2026-09-14~09-22）

### 2.2 对「增速看板」的直接回答

> **用户需求**：「当日 GMV ÷ 前 7 日同日 GMV」，每类目 TOP3，每日刷新。

| 结论 | 依据 |
|---|---|
| ✅ **能回溯** | 自然日（date_type=7）最多回 **266 天**（2025-12-31 起） |
| ⚠️ **不是单日** | 罗盘给的是**区间累计值**，「近 7 天」= 截止日的最近 7 天滚动 |
| ⚠️ **「近7天」窗口只回 6 天** | date_type=21 当前范围 09-17~09-23，**今天取和昨天取会重叠** |
| ✅ **正确做法** | 用 **date_type=7（自然日）** 自己指定两段**不重叠**的 7 天窗口（如 9/18-9/24 vs 9/11-9/17），比值即增速 |
| ✅ **不用攒历史** | 第一天就能出数，只要每次固定取两段等长窗口 |

### 2.3 页面上的时间选项

`近1天 / 近7天 / 近30天 / 更多 →（自然日 / 自然周 / 自然月 / 大促）`


| 字段 | 含义 |
|---|---|
| `cate_pay_amt` | 用户支付金额 |

### 4.4 市场 → 行业机会 → 类目挖掘

**页面**：`/shop/chance/category-mining`

**页面元素**：
- Tab：挖掘潜力类目 / 类目爆款分析 / 应季日历

- 「应季爆发类目」（如护手霜 +361.26%）
- 类目分析表（可勾选 增速快/成交高/竞争小）

**接口**：

```
GET /compass_api/shop/product/product_chance_market/dig_cate_cards
?date_type=21&begin_date=...&end_date=...
&industry_id=5&first_cate_id=1000003462&content_type=1

GET /compass_api/shop/product/product_chance_market/dig_cate_list
?date_type=21&begin_date=...&end_date=...
&cate_tag_list=2&content_type=1&first_cate_id=1000003462
&source_biz_type=1&page_size=10&page_no=1&is_asc=false
&sort_field=pay_amt_incr_rate          # 按成交增速排序
```

**字段映射**（`basic_meta` 自带口径）：

| 中文列名 | 英文字段 | 官方口径 |
|---|---|---|
| 类目信息 | `cate_info` | 含 `category_id` / `category_name`，附 tags：`成交高第N名`/`增速快第N名`/`竞争小第N名` |
| 用户支付金额 | `pay_amt` | — |
| **成交增速** | `pay_amt_incr_rate` | **用户支付金额环比上一周期的增长百分比** |
| **需求供给比** | `demand_supply_rate` | **搜索/推荐等多渠道潜在购买需求订单数 ÷ 近1天在架商品数，越大竞争越小** |
| 最高成交价格带 | `top_pay_price_bin` | — |
| 自然流量成交占比 | `natural_flow_pay_amt_ratio` | **自然流量支付金额 ÷ 总支付金额，越大付费占比越小** |
| 热卖商品 | `top_product_list` | id / name / image / sale_price / url / qr_code |

**每个指标还带 `*_trend` 字段**（含 `axis_data` 按天序列，可直接画趋势线）。

**实测样本**（个人护理，近 7 天）：
- 面部护理套装：成交增速 68.01%（增速快第 6 名）、¥7.5亿-¥8亿（成交高第 1 名）、需求供给比 17.29

## 五、已知坑与禁令

| # | 坑 | 处置 |
|---|---|---|
| 1 | 响应体在 network 工具里是 base64 压缩，看不到明文 | **在页面上下文里 `fetch` 重发**，拿明文 JSON |
| 2 | `compass_general_table_value` 是 JSON 字符串 | 二次 `JSON.parse` |
| 3 | `msToken` / `a_bogus` 每次变化 | 从页面上下文取，**不能硬编码** |
| 4 | `rank-goods` 页面渲染空白 | 商品榜用 `rank-product` |
| 5 | 「近7天」窗口只回 6 天 | 要严格不重叠的 7 天窗口，用 `date_type=7` 自然日自定义 |
| 6 | 罗盘人群是「本店」视角 | 竞品人群画像走星图/飞瓜，不走罗盘 |
| 7 | 金额全是区间值 | 要精确值需换源；罗盘口径下不要假装精确 |
| 8 | 浏览器单例 | 不要并行操作浏览器；不要关用户的 Chrome |
